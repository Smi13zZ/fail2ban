# fn-fail2ban 26.11.5 · 通知、存储、更新三块补齐

26.11.4 之后，这个面板在同一条产品线上还差三块能力：通知只支持 7 种渠道、没有投递留痕；
没有存储视图，日志和旧备份只能 SSH 进去手删；没有版本自检与一键升级。这一版把这三块补齐，
同时把工程质量闸门和打包发布流程做成一条命令可复跑的一套。

## 1. 通知

**渠道 7 → 11。** 新增 Server 酱、PushPlus、WxPusher、Telegram；原有 Bark、钉钉、
企业微信（群机器人 / 应用消息）、飞书、Slack、自定义 Webhook 的键名与字段语义一字未改，
已保存的配置能直接继续发。

**字段元数据驱动。** 每个渠道的字段带中文与英文两份标签、提示、占位符与默认值，
由后端下发、前端按当前语言渲染，切语言当场生效。前端不再硬编码任何渠道字段。

**密钥只在服务端打码。** 接口回传时密钥字段统一替换成掩码；提交时掩码或空串表示沿用原值，
只有真填了新值才替换，按 id 与原配置合并。这道合并写在服务端——整份设置回传时
`channels` 是数组，前端收窄只是第二道防线。

**推送改双语。** 标题「中文 / English」，正文「中文段 + 空行 + 英文段」。封禁、解封、
服务异常、服务恢复与测试通知全走同一套，测试通知也是双语的。

**新增投递记录。** 每次推送留一条，成功失败都记，失败写明原因（HTTP 状态码或上游返回的
错误码）。字段固定为 id / at / event / channel / channel_id / type / ok / detail / title / body，
**绝不含渠道密钥**；写入前还会用该渠道自己的密钥值把正文里可能回显的明文擦掉。
环形缓冲 300 条，写临时文件再原子替换，文件损坏按空处理。

**成败判定不只看 HTTP 200。** 钉钉与企业微信看 `errcode`、Telegram 看 `ok`、飞书看 `code`、
Server 酱看 `code=0`、PushPlus/Bark 看 `code=200`、WxPusher 看 `code=1000`。
实测构造「HTTP 200 + ok:false」时判失败——这正是只看状态码会漏掉的静默失败。

## 2. 存储

新增「存储」页：列出数据目录下各文件的占用（字节数与文件数）、归档备份清单与当前版本，
给出合计。子目录里的条目（升级安装日志在 `update/` 里）标「已计入上级目录」，
不计入总量，避免重复统计。

三个清理入口（清理日志 / 清理旧备份 / 全部清理），每个都会先说明预计回收多少。

- **运行中的日志只能就地截断。** 面板以追加方式持有 `server.log` 的句柄，`os.remove`
  只删目录项、空间仍留在旧 inode 上，这正是「清了没变小」的原因。实测清理前后 inode 相同、
  大小归零。
- **越界一律拒绝。** 清理路径经 realpath 校验，只在本应用目录内；软链接、`..`、
  指到目录外的路径都不处理。
- **升级进行中整体拒绝。** 下载或安装时返回 409，避免删掉正在写的安装包。
- **启动时自动清一次。** 放在新进程启动后，而不是下载完成时——升级会替换面板进程，
  旧进程里删文件有可能删到正在安装的那一个。保留最新 2 个完整包、删掉全部半截下载、
  当前运行版本与 `rollback.fpk` 永不删除（后两者不占 keep 名额）。

## 3. 版本检查与一键更新

**新增「更新」页**：当前版本 vs 最新版本、状态条、发布说明、安装包列表、检查更新与一键更新。
只有「发现新版本」着色，已是最新与检查失败都走中性色——正常状态不该看起来像需要处理。

**版本检查三层退路**：GitHub API → releases.atom → 扩展资产页面 HTML。任何一层成功即可。
仓库不存在或还没有 Release 是**正常答案**（`reason=not_found` / `no_release`），
返回结构不抛异常。版本号按数值比较，26.11.10 大于 26.11.9。

**节流**：成功缓存 15 分钟、失败冷却 60 秒；时间戳只在查询成功时写，
一次断网不会让下一次补查再等 15 分钟。服务端轮询启动 60 秒后查第一次、之后每小时一次，
与浏览器开没开无关；循环体整体捕获异常，断网只记日志。

**一键更新**依次：下载到 `.part` → 校验（tar 成员含 manifest 与 app.tgz、appname、version）
→ 写安装脚本到 `@appdata`（`@appcenter` 在卸载时会被删）→ `start_new_session` 分离执行
→ stop / uninstall / install / start。

两个关键判断：

- **成功与否看版本号变成目标值，不看 install-fpk 的退出码**——它对着已装应用会静默什么都不做。
- **回滚只在应用真的不见了时才做。** 版本号仍是旧值说明卸载或安装被拒、原安装完好，
  此时回滚等于卸载再装一次，会亲手拆掉一个能用的实例。

升级时喂给向导的 `enable_ssh_jail` 一律传 false：`install_callback` 收到 true 会**无条件**
把 sshd Jail 的 enabled 写成 true，等于替用户重新打开一个他自己关掉的防护。

## 4. 界面与工程

- 侧栏新增「存储」「更新」两项；更新有可用版本时侧栏打红点。
- 升级遮罩：进度区固定高度（下载 → 安装重启切阶段时不跳高）；进度只增不减；
  没有总量可测的阶段显示「准备中…」而不是假装有百分比；装完自动重载。
  轮询排在阻塞请求**之前**——后端是在 `/api/update/install` 里同步下载的，
  先 await 再轮询等于下载全程零进度。
- 手机端：顶栏工具按钮折到第二行右对齐（390px 一排放不下标题 + 徽标 + 两个按钮）；
  存储表在窄屏隐藏路径列，把宽度还给项目名与大小。
- **工程闸门 8 道，一条命令跑齐**：结构自测（变异样本）→ 结构检查 → Python 编译 →
  i18n 自测 → 前端 JS 语法 → i18n 一致性 → CSS 与静态资源 → 文档链接。
- **新增包自检**：可执行位、外层图标、九档图标齐全、包内无临时文件、checksum 与 app.tgz
  实际 md5 一致、包内版本与源码一致，以及 `cmd/*` 与 1.7.0 的逐字节比对。
- **CI**：推 `v*` 标签触发构建，只有标签名等于「v + manifest 版本」时才发布 Release。

## 已知限制

- **面板内的「一键更新」在这台测试机上报 `appcenter-cli uninstall` 被拒**
  （「please uninstall it from Web UI」），这是 fnOS 对第三方应用的限制，与代码无关。
  安装脚本已经会在这种情况下不执行回滚、把原安装原样留着（实测确认）。
  真正可用的升级路径仍是应用中心 Web UI；一键更新在解除该限制的设备上可用。
- 本次实装验证用的是「解包 + 逐文件替换 + 重启」的方式，因为 `install-fpk` 对已装应用
  直接返回 "is installed"、`uninstall` 拒绝。包本身的结构与权限由
  `tools/inspect_fpk.py --strict` 单独验证（PASS）。
- 仓库 `Smi13zZ/fail2ban` 尚未发布，所以设备上版本检查的默认结果是「找不到更新仓库」，
  这是预期状态；发布后即恢复。
- **生产机 fnos-prod 未做任何改动**，升级由用户在应用中心 Web UI 自行操作。
