# Fail2ban 26.11.52 交付说明

修一键升级「面板回来了但页面不动、只能手动刷新」。

## 一、根因

旧代码按「轮询连续失败 180 次」判超时，间隔 400ms → 折合 **72 秒**。

一次升级的实际耗时：

| 步骤 | 耗时 |
| --- | --- |
| 停服务 | 1～3 秒 |
| install-local 卸载 + 安装 | 20～60 秒 |
| appcenter-cli start | 10～30 秒 |
| 面板起来 + 读 manifest | 5～20 秒 |

整轮实测 **60～150 秒**。慢一点的机器必然在面板还没回来时就被判超时：
遮罩停在原地不动，只剩「立即重新加载」按钮 —— 看起来就是「不能自动重载」。
而且升级完成的那一瞬间，浏览器往往正好处在「接口连续失败」窗口里。

## 二、改法

**轮询改用 10 分钟时间预算**（`UPDATE_WAIT_MS`）：

- 期间接口失败一律当作「面板暂时不在」，不再计失败次数；
- 只要还在预算内就继续等，版本号一变就收尾并自动重载；
- 超时才显示「等待超时，请到飞牛应用中心确认安装状态」。

## 三、顺带：刷新后能接着跟

升级要卸载重装，页面必然被打断。用户在途中刷新一下（或浏览器自己重载），
旧代码就再也不知道「刚才有个升级在跑」，面板回来了什么都不说。

现在升级开始时把「升级前版本号」写进 `sessionStorage`，页面载入时：

| 情况 | 行为 |
| --- | --- |
| 版本号已变 | 清掉标记，正常进入新版本 |
| 版本号没变 | 还在途中，重新显示遮罩并接着轮询 |
| 升级成功 | 清掉标记 + 1.5 秒后自动重载 |
| 后端明确报 failed | 清掉标记，不留残留 |

## 四、实测

| 场景 | 结果 |
| --- | --- |
| 版本号按预期变化 | 1.5 秒后自动重载，标记已清（`loads` 由 1 → 2） |
| 升级途中刷新页面 | 遮罩重新出现：标题「正在升级」、阶段「准备中…」 |
| 后端报 failed | 标记清除，不残留 |

> 注意：这两项用的是页面内注入的假 `update` 接口（只改轮询与收尾逻辑，
> 不触发真实安装），真机升级流程未改动。
