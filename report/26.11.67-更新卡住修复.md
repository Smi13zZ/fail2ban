# Fail2ban 一键更新后卡在遮罩 —— 生产机问题定位与修复（2026-11-19）

## 现象

生产机 `fnos-prod`（192.168.1.10 / Chin）从 26.11.65 一键更新到 26.11.66 后，
弹窗停在「正在更新到 v26.11.66 / 已更新到 v26.11.65，正在刷新… / 准备中…」，
页面怎么刷新都回不来。面板本身是好的。

## 只读巡检结论（生产机未做任何变更）

- `appcenter-cli list`：`fn-fail2ban 26.11.66 running`，新版本确实装好并起来了。
- `/api/health`：`version 26.11.66, uptime 469s`。
- `/api/update/progress`：`phase=idle`、`outcome=succeeded`、`current=26.11.66`。
- `install.log` 尾部：`[Info]Installation complete.` + `=== 已升级到 26.11.66 ===`。

即：升级全程成功，卡住的只是**发起升级的那个浏览器页面**。

## 根因（两层叠加，缺一不致命）

1. **新的一轮继承了上一轮的结论**。安装脚本只往 `install.log` 追加，上一轮留下的
   `=== 已升级到 vX ===` 一直在文件尾部。新的安装请求一开始（阶段还是 `downloading`），
   `progress()` 就无条件执行 `_outcome(_tail(...))`，把这句旧话识别成 `succeeded`
   发给了前端。
2. **前端判定完成的那一刻，服务正好要停**。`pollUpdateProgress` 看到
   `outcome === 'succeeded'` 立即 `finishUpgrade(true)`，1.5 秒后 `location.reload()`。
   而安装脚本的下一步正是 `stop → uninstall → install`，刷新正好撞进这个离线空窗，
   浏览器停在错误页上，再也不会自己回去。

真机复现（测试机 26.11.66，同版本代码）：点下更新后 **0.2 秒**就读到
`phase=downloading, outcome=succeeded` —— 与生产机现象完全对应。

## 修法（26.11.67）

后端 `installer.py`：

- 新增 `_reset_install_log()`，每轮 `install()` 开头清空安装日志，历史记录不再冒充本轮结论。
- `progress()` 在 `checking / downloading / installing` 阶段一律不下发 `outcome`
  （只在本轮跑完、阶段回到 `idle` 或 `failed` 后才给）。

前端 `app.js`：

- 主判据收紧成「`outcome === 'succeeded'` **且** `phase === 'idle'`」。
- 新增 `reloadWhenBack()`：装完后不再固定 1.5 秒刷新，而是先探一次 `api/meta`，
  能答上来说明新进程已经在服务，这时才刷新；探不到按 800ms 退避重试（最长约 80 秒）。
  重试超过约 8 秒会把遮罩上的「立即重新加载」按钮放出来，万一浏览器停在断网错误页
  用户还能自己点一次。

## 遗留说明

- 生产机**没有做任何写操作**：全程只读巡检 + 用户自己已完成的升级。修复需要用户在
  应用中心升级到 26.11.67 才生效。
- 端到端演练时我在测试机上临时造过一份 26.11.99 测试包（用于让更新流程真的跑一遍
  下载→停服→安装）。过程中用 PowerShell `Set-Content` 改文件把中文写坏，产生了
  BOM 与乱码，导致那个测试包里的 `server.py` 语法错误。**已从备份还原**，并逐文件
  核对本地源码与已发布的 v26.11.67 完全一致（server.py / manifest / installer.py /
  app.js 全部 MATCH）。测试包与临时服务已全部清理，测试机现为 26.11.67 正常运行。
- 教训（已踩第二次）：改中文源码一律用 Python 以 UTF-8 读写，不要用
  PowerShell `Set-Content`。
