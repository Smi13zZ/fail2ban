# 官方 1.7.0 包与我的包 · 初始安装方式对比

对比对象：

| | 文件 | 大小 | sha256 |
| --- | --- | --- | --- |
| 官方 | `fn-fail2ban_1.7.0_all (1).fpk` | 111,602 | `762b8d68…` |
| 我的 | `fn-fail2ban-26.11.4-all.fpk` | 291,407 | — |

## 结论先说

**安装方式完全一样，没有差别。** 两者都是同一套 fnOS 原生应用安装流程：
相同的 `appname`、相同的 `service_port`、相同的 `desktop_applaunchname`、
相同的网关接入方式（iframe + `app.sock` + `/app/fn-fail2ban` 前缀）、相同的文件落点。
官方包能做到的「在应用中心点安装、桌面出现图标、点开进入面板」，我的包一模一样。

**唯一的实质差别是安装向导的第一步被删掉了**，因为面板不再有登录页：

| | 官方 1.7.0 | 我的 26.11.4 |
| --- | --- | --- |
| 向导步骤 1 | 「管理面板账号」：管理员用户名 + 管理员密码 | **已删除** |
| 向导步骤 2 | 运行环境（自动安装 fail2ban） | 同 |
| 向导步骤 3 | 初始防护策略（bantime / maxretry / ignoreip） | 同 |

删掉那一步是「移除登录页」这一项需求的直接结果 —— 没有登录页，收密码就没有意义。
配套地，`install_callback` 里写 `credentials.json` 的那段也一并去掉了。

## 逐项核对

### 安装入口（完全一致）

```
appname               = fn-fail2ban      ← 相同
version               = 1.7.0 / 26.11.4  ← 版本号（预期不同）
platform              = all              ← 相同
service_port          = 18752            ← 相同
desktop_uidir         = ui               ← 相同
desktop_applaunchname = fn-fail2ban.main ← 相同
os_min_version        = 1.1.8            ← 相同
checkport             = true             ← 相同
ctl_stop              = true             ← 相同
source                = thirdparty       ← 相同
```

`ui/config` 的 `gatewayPrefix` / `gatewaySocket` / `url` / `type` 四项也完全相同，
只有 `title` 不同（「Fail2ban 防护」→「Fail2ban」，这是你要求的改名）。

### 生命周期脚本

官方 17 个外层文件，我 17 个，文件名完全相同，权限完全相同（`cmd/*` 全部 0755，其余 0644）。

忽略行尾差异后逐字节比对：

| 状态 | 文件 |
| --- | --- |
| **完全相同** | `cmd/config_init`、`cmd/env.sh`、`cmd/install_init`、`cmd/main`、`cmd/uninstall_callback`、`cmd/uninstall_init`、`cmd/upgrade_callback`、`cmd/upgrade_init`、`wizard/uninstall`、`config/privilege`、`config/resource` |
| **不同** | `cmd/install_callback`（去掉写凭证）、`cmd/config_callback`（去掉重置密码）、`wizard/install`（去掉账号步骤）、`manifest`（版本号/名称/changelog）、两个 ICON |

升级、卸载、启动停止这几条最关键的通路**一个字节都没动**，所以覆盖升级与卸载行为与官方版一致。

### 我的包多出来的两个东西

**1. `app.tgz` 里多一层 `config/`**

官方 `app.tgz` 内只有 `bin/ ui/ web/`；我的多了 `config/privilege` 和 `config/resource`，
内容与外层 `config/` 完全相同（md5 逐一核对过）。

来源：早前从生产机已装目录提取源码时，`target/` 下带着这两个文件，一起进了源码树。
影响：**无害**。这两个文件是 fnpack 的布局声明文件，实际生效的是外层那份
（设备上 `/var/apps/fn-fail2ban/config/` 与 `/vol1/@appcenter/fn-fail2ban/config/`
内容一致，都是外层写入的）。包里没有任何代码引用 `target/config`。
属于多余的冗余，不是错误。

**2. 图标从 2 档变成 9 档**

官方只有 `icon-64`/`icon-256` 与下划线版本共 4 个文件（且 `-` 与 `_` 两套内容重复）。
我的按 `icon_{0}.png` 约定给全 16/24/48/64/72/96/128/256/512 九档 ——
应用中心按设备密度取文件，缺档就是空白格子，所以这是必要的补全。

### checksum 字段

官方 manifest 写 `checksum = a84cecbdd688f69a27d8caceaa63e2ce`，
正好等于它自己 `app.tgz` 的 md5。我核查了 5 个交付包，**全部与实际 `app.tgz` 的 md5 一致**
（fnpack 打包时会重算这个字段），不需要手工维护。

### 一个容易看漏的点：行尾

官方 `cmd/*` 和 `manifest` 是 **CRLF** 行尾，我的是 LF。
Linux 上 `#!/bin/bash\r` 会让内核找不到解释器（`bad interpreter`），
所以官方那套脚本能在设备上跑起来，说明 fnOS 安装时会做行尾归一化 / 重新生成 —— 实测确认过：
部署到设备的 `cmd/main` 是 `CRLF=0 LF=119`。

我的包本来就是 LF，属于更稳妥的形态，不影响安装。

## 安装方式对生产机的实际影响

| 场景 | 官方 1.7.0 | 我的 26.11.4 |
| --- | --- | --- |
| 应用中心点安装 | 弹向导，3 步 | 弹向导，**2 步**（不用填账号密码） |
| 装完点图标打开 | 显示登录页，要输账号密码 | **直接进面板** |
| 局域网内其他设备访问 | 要登录 | 按 CIDR 白名单放行（默认回环 + 内网段） |
| 从 1.7.0 覆盖升级 | — | 配置沿用，`credentials.json` 保留不删（回退旧版仍可登录） |

## 结论

安装方式没有变化，只是少了「填管理员账号密码」这一步。
如果你的生产机现在跑的就是官方 1.7.0，直接上传我的包覆盖升级即可：
向导只问运行环境和初始防护策略，装完点图标直接进面板，原有的 jail 配置、通知设置、
白名单全部沿用。
