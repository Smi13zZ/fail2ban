# Fail2ban 26.11.53 交付说明

一键升级的确认框换成站内模态。

## 一、为什么

原先用 `window.confirm`，两个问题：

1. **它是浏览器面板，不属于这套界面** —— 与旁边的按钮、卡片是两套视觉；
2. **同步阻塞** —— `confirm()` 返回前渲染线程停住。升级流程里遮罩已经起来、
   轮询正在跑，此刻弹一个原生确认会把轮询一起卡住，看起来就像升级卡死。

## 二、改法

新增站内模态（`.modal-wrap` / `.modal`），结构与业内同款面板的确认框一致：
标题条 + 正文 + 底部「取消 / 主按钮」。

- 打开时焦点给主按钮，回车即确认；
- 点遮罩空白处等于取消，点框内不关；
- 标题与主按钮都用「一键更新」，与触发它的那个按钮同名。

**只有一键升级走这个模态。** 其余 13 处危险操作（解封、删渠道、恢复备份……）
仍是同步 `confirm`：它们的调用点是 `if (!confirmDanger(…)) return;` 这种守卫写法，
改成异步要把 14 个函数体全部包一层回调，改动面大且容易漏；而它们都不会在遮罩
期间弹出，没有阻塞轮询的问题。这一点写进了代码注释，避免以后被「统一一下」改回去。

## 三、实测

| 项 | 结果 |
| --- | --- |
| 点「一键更新」 | 站内模态出现，宽 420px |
| 标题 / 按钮 | 「一键更新」/「取消」「一键更新」 |
| 正文 | 将下载 v26.11.99 并重启面板完成升级，过程中面板会短暂无法访问。继续？ |
| 点确认 | 遮罩起来、轮询开始，确认框关闭 |
| 版本变化后 | 1.5 秒自动重载，`sessionStorage` 标记清空 |

以上用页面内注入的假 `update` 接口验证，不触发真实安装。
